# Idiomate v1.2 Implementation Plan

> Driven by real-use feedback. Theme: **make it actually track, teach, and stick.** TDD, exact paths, commit per workstream. Claude reviews each. Codex owns `server/` + `shared/`; the reviewer owns `client/` UI polish (but Codex may add plain, functional UI for new data so it is testable).

Sequencing: **P0 (W1, W2) first** (they fix a broken core loop), then P1 (W3-W6), then P2 later.

---

## Context the implementer needs

- The backend already persists every mistake: `annotations(session_id, paragraph_idx, span_text, error_type, hint, explanation, model_rewrite, rule, rule_example, user_rewrite, accepted)` and `error_tally(error_type, count, last_seen)`. The data layer is fine; the problem is **when** it records and **how** it is surfaced.
- `rules.ts` holds named grammar/Chinglish principles (authored by the reviewer). `taxonomy.ts` holds the 11 error types + examples. Reuse both; do not rewrite.
- News: `server/src/news.ts` `fetchHeadlines(topic)` already hits Google News RSS but returns titles only.

## P0 - W1: Live error tracking (fixes "My patterns is dead")

**Problem:** errors are written to `error_tally`/`annotations` only on the global "Save session" click (`POST /api/sessions`). Users coach + submit a paragraph rewrite and see no profile change.

**Fix:** record the moment a paragraph rewrite is submitted, per paragraph.

**Files:** `server/src/routes/sessions.ts` (or a new `server/src/routes/paragraphs.ts`), `client/src/App.tsx`, `client/src/components/CoachPanel.tsx`, tests.

- [ ] Add `POST /api/paragraph-result` accepting `{ promptId?, date?, paragraphIdx, paragraph, rewrite, annotations: SubmittedAnnotation[] }`. It: creates/【reuses】a session row for today's prompt, `insertAnnotations`, `recordErrors(errorTypes excluding vocab_suggestion)`, and `incrementVocabUsed` for accepted vocab suggestions. Idempotency: re-submitting the same paragraphIdx for the same session should replace its prior annotations (delete-then-insert by session+paragraph_idx) so counts do not double.
- [ ] Client: `CoachPanel.submitRewrite` (compared phase) calls this endpoint directly via a new `recordParagraph()` api fn, then the App bumps `profileKey` so the dashboard refetches immediately. The global "Save session" button becomes optional (keep it to finalize `final_text`, or remove it).
- [ ] Test: posting a paragraph result updates `error_tally`; re-posting the same paragraph does not double counts.

## P0 - W2: Contextual ruleExample (kills the canned "Heavy rain / She is teacher" repetition)

**Problem:** the model copies the generic example from the injected taxonomy/rules into `ruleExample`, so every word_choice issue shows "Heavy rain made a big influence...". Feels canned and fragmented.

**Files:** `server/src/brain/prompts.ts` (`assembleCoachPrompt`).

- [ ] Add explicit instruction: `ruleExample.before` MUST be taken from (or closely based on) the user's own text for THIS issue, and `ruleExample.after` is its corrected form. NEVER copy the example sentences from the Taxonomy or Rules sections; those are references for you, not output. If no faithful minimal pair fits, generate a fresh one specific to this error - do not reuse a reference example.
- [ ] (Optional) Drop the example sentences from the injected `taxonomySnippet`/`rulesSnippet` (keep names + principles only) to remove the temptation to copy. Keep one example per rule at most.
- [ ] No test change required (prompt wording); verify live.

**Files:** `server/src/db/dal.ts`, `server/src/routes/profile.ts`, `client/src/components/ProfileDashboard.tsx` (reviewer will restyle).

- [ ] DAL: `getMistakeRanking(db)` -> per error_type: `{ errorType, count, lastSeen, recentExamples: [{ span, userRewrite, rule, date }] }` (join `annotations` + `error_tally`, top 3 recent instances per type). `getMistakeLog(db, errorType?, limit)` for drill-down.

## P1 - W4: Systematic grammar lessons (learn, not fragmented)

**Goal:** for your top recurring mistakes, one consolidated lesson instead of scattered hints. Chinglish gets the mindset "why."

**Files:** `server/src/brain/rules.ts` (extend with `mindset` notes for Chinglish rules), `server/src/brain/prompts.ts` (`assembleLessonPrompt`), `server/src/routes/lessons.ts`, client view.

- [ ] Extend Chinglish-family rules (calque, redundancy, noun_plague, over_explanation) in `rules.ts` with a short `mindset` field: the Chinese->English thinking difference behind the error. (Reviewer authors these - original wording.)
- [ ] `GET /api/lesson?type=` -> for the given error type (default: the user's #1 recurring): returns the rule(s), the principle, the mindset note, the user's own past instances of this type (pulled from `annotations`), and 4-6 comparison before/after pairs (seed pairs from rules.ts + LLM-generated extras tailored to the user's recent mistakes of that type). zod-validate.
- [ ] **Output may be bilingual:** explanations, the "why/mindset", and the principle may be written in Chinese (the learner's L1) for clarity; the before/after example PAIRS stay in English. Make this explicit in `assembleLessonPrompt`.
- [ ] UI: a "Learn" panel that opens from a ranking row -> shows the lesson with the user's own past errors + multiple comparison examples.

## P1 - W5: Content analysis + sourced research (after polishing)

**Goal:** after the language polish, evaluate the *content*: is the argument correct and convincing, what other angles to consider - grounded in real-time news with links.

**Files:** `server/src/news.ts` (return links), `server/src/brain/prompts.ts` (`assembleResearchPrompt`), `server/src/routes/research.ts`, client view.

- [ ] `news.ts`: add `fetchNews(query)` returning `{ title, link, source }[]` (parse RSS `<item>` `<title>`+`<link>`). Keep `fetchHeadlines` for prompts.
- [ ] `POST /api/research` body `{ essay }`:
  1. LLM analyzes the essay -> `{ analysis (strengths + gaps), otherAngles: string[], searchQueries: string[] }`.
  2. For each query, `fetchNews` top ~2 -> `sources: [{ title, link, summary }]` (LLM one-sentence summary each).
  3. **Evidence-integrated rewrite (the payoff the user asked for):** a second LLM step takes the essay + the gathered sources and produces `integratedEssay` - the user's essay with the relevant evidence woven in **at appropriate positions**, plus `integrationNotes: [{ insertedAfter, what, why, structurePart }]` explaining WHERE each piece was inserted, WHAT it adds, and WHICH structural slot it fills (topic sentence / claim / evidence / commentary). The integrated essay should model good structure (topic sentence -> claim -> evidence + citation -> commentary).
  - Return `{ analysis, otherAngles, sources, integratedEssay, integrationNotes }`. Best-effort: if news fails, still return analysis + a structure-only integratedEssay (no external citations).
- [ ] UI: a "Content check" section under the coach output: argument critique + angles to consider + the source list (`headline (link) - one-sentence summary`) + the **evidence-integrated essay** with the integration notes shown beside the inserted parts.
- [ ] Test with stubbed fetch + mock provider: research returns sources with links + summaries AND an `integratedEssay` with `integrationNotes`; survives a news fetch failure (still returns analysis + integratedEssay).

## P1 - W6: Writing structure guidance

**Goal:** suggest the ideal structure (topic sentence -> explanation -> evidence + commentary -> ...) and flag where the draft deviates.

**Files:** `server/src/brain/prompts.ts` (`assembleStructurePrompt`), `server/src/routes/structure.ts`, client view.

- [ ] `POST /api/structure` body `{ draft }` -> `{ idealOutline: [{ part, purpose }], observations: [{ part, status: 'present'|'weak'|'missing', note }] }`. zod-validate.
- [ ] UI: a compact "Structure" panel: the recommended skeleton + per-part status against the user's draft.
